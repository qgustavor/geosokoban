# GeoSokoban Prototype Design Document

A sokoban-like game that helps you learn geography.

This is the design document of a prototype project. The idea behind this project is designing a simple self-contained sokoban-like game which, depending on the findings from this prototype, might be integrated to an existing geography game called "GeoJogos". This prototype isn't meant to replace nor compete with the original game, being just an isolated self-contained prototype meant for idea exploration. In case the original game author wishes, this game might be taken offline after we reach the findings we need for the development of the full game.

## Prior work

The main prior work behind this prototype is the game GeoJogos, which is a mini-game pack of geography games. Last month (IIRC) it included a new game called "GeoSokoban", which is a sokoban-like game with programmatically generated levels.

Reminder: this prototype will share the same name because the plan for this prototype isn't for replacing or competing with the original mini-game, but for finding ideas and improvements upon it, fixing some of player's issues and improving its educational aspect.

The current interaction of GeoSokoban works like this:

- Generated levels follow a rectangular layout with randomly placed walls, randomly placed boxes with country flags and randomly placed targets.
- The game checks if levels can be solved, thus all levels can be solved using simple block pushing rules.
- The player is a compass.
- The game has a level select, allowing players to choose a continent (which will determine which flags will be used) and which difficulty (which changes the level size and number of placed objects - walls and boxes).

Thus, this interaction also have lots of issues, educational and gameplay wise:

- The main issue from this game is that the flags only work as a thematic skin. There is nothing for the player to learn from, since the player just need to move the flags to their respective targets, gaining no geography knowledge in those actions.
- To be fair, if there was some geography knowledge for the player to gain, would be just seeing the flags.
- Gameplay wise, the levels, being randomly generated by placing objects at random places and checking if they can be solved, results on boring levels without usual sokoban-like elements.
- The layout of the game, with plain walls and floors, makes it kinda boring too.
- There is a move counter, a timer and a score counter which decreases as the player moves, which adds extra friction to the player.

Then, in order to solve the above issues, we checked some sokoban-like games in itch.io, mainly those designed by Hempulli, a creator which many free to play sokoban-like mini-games. From those, we noticed those patterns:

- Most popular sokoban-like games in itch.io do not follow the original Sokoban game flow where the player just pushes boxes, instead, they use two main ingredients from the original game - box pushing and grid-based - and mix with something else.
  - Baba is You mixes sokoban with dynamic rules.
  - N-step Steve mixes sokoban with a movement counter which can be reseted with flags which can be moved.
  - Handshakes mixes sokoban with limited moves and gates which split the player (hands) turning them into boxes.
  - Snakebird mixes sokoban with gravity.
  - Patrick's Parabox mixes sokoban with recursive levels.
  - Theta and Paralldox on Worldlines mixes sokoban with multiple timelines and other cursed stuff.
  - SquishCraft is even more cursed.
- Most sokoban players rely on human-designed levels using some strategies:
  - https://www.games4brains.de/sokoban-leveldesign.php shows some strategies like using trapdoors, sliding doors and design strategies.
  - https://sokoban.dk/articles/1596-2/ shows that auto-generators can be used to aid level design.
  - https://healeycodes.com/building-and-solving-sokoban add details about how a sokoban solver can be designed.
  - https://sokoban-jd.blogspot.com/2015/02/how-to-build-sokoban-level.html shows other design strategies.
- Most modern games avoid the old-style look of sokoban games:
  - Most levels in Baba is You have large rooms for the player to work with, while still using sokoban strategies like dead zones to prevent the player from finding exploits in levels. Also, instead of plain walls and floors, it uses a lot of decorative objects, some animated even.
  - N-step Steve levels can be divided into hallway levels and puzzles and, while hallway levels still follow the rules of the game (i.e. the player can die on then) they have lots and lots of extra room. Puzzles, on the other hand, are more constrained like old sokoban.
  - Theta and Paralldox on Worldlines levels work on a 3D level, thus, instead of walls, some levels are delimited by voids.
  - Both Stephen's Sausage Roll and A Monster's Expedition works on 3D islands.
  
We also checked some GMTK videos.
  
## Design choices

Based on the above ideas, we reached into some basic design choices for the prototype:

- Because this is meant to be a prototype meant for idea exploring, we will design the game in the form of a web game that will be distributed in GitHub Pages.
- Because JavaScript/HTML/CSS is a English-first language, in order to avoid language context switching, we will develop mostly in English (like we are doing now with this design document). Even if the original author does not know English, their AI do know. Also, Google Translate exists.
- We want to allow this prototype to be playtested with Portuguese, Spanish and English speaking players, so it should be translated to those three languages.
- The game of the prototype will be "GeoSokoban", but we need to add something to make it clear it's a prototype. Maybe adding a "PROTOTYPE" next to the logo and adding a link to the original game.
- The prototype should be FOSS, so the original author can see how it was developed and take ideas from it into the original game.
- Despite it being a prototype, it should follow the best concepts and ideas for organizing a FOSS project like:
  - Using Vite for the bundling of the web app, since it will be distributed as a web app.
  - Using a framework for handling DOM interactions: Vue, because it's simple, thus more likely for the original author to understand).
  - Using a code style guide: Standard JS (or Neostandard) because, by omitting semicolons, it makes it easier to read the code (I find semicolons distracting, also, it makes JS kinda Python-like, which I find interesting).
- Inspired by GTMK, the game should use vector graphics, since that was the solution for handling multiple display resolutions in GMTK's magnet game (Mind Over Magnet).
- Also inspired by GTMK, the game should be on the easier side, since our target audience isn't die-hard puzzle game enthusiasts, but geography students. That said, following GTMK's video on game difficulty scaling, since we are making an easy game, we can balance it out adding challenges for players willing a harder game (we will discuss it later).
- Unlike the original game, because it's just a prototype, there will be no server-side components (like a ranking).
- We needs a credit page to include details about the original game and inspirations, otherwise you might think we need to include all this info in the main menu and then it will become a mess with a lot of information for players to dig.

From my experience working with AI before, we need to also set some coding rules:

- Comments in code should always comment the code next to it, never refactoring changes. AI tools often has a bad habit of including comments about changes due to StackOverflow and coding tutorials.
- UI facing strings should never include implementation details. That's a bad habit from coding tutorials.
- UI facing strings should be simple to read and concise. Again, a bad habit from coding tutorials.

With the above in mind, now let's talk about gameplay and improvements upon the original game:

- The main difference from the original GeoSokoban game which I have in mind is moving away from "a sokoban-like game with a geography skin" to a "a geography game with sokoban-like mechanics".
- I idealize the game following this workflow:
  - A main game selection area (similar to the current game difficulty selector) but instead of difficulty levels and continents there will be three modes: daily challenge, random game and story mode.
  - Daily challenge will load the same level for every player based on a generated level using the current date as a seed. Level generation will be discussed later.
  - Random game allows the player to load a randomly generated level (in case they wants to play more levels other than just the daily one).
  - Story mode loads a set of human designed levels with story points, being a game mode which allows for more educational content like: gradual introduction of puzzle elements (from easier to harder - but never too hard) and addition of geography elements as story points. My idea for this game mode is for the player guide the character into an around the world travel, where the main character will show to the player trivia points of the countries they go though.
  - On the end of a game round, there should be an option for the player to share their move count, in order to allow them challenging other players. Remember to add to the prototype documentation a recommendation for the original game author for, when implementing this ideas on the original game, keep a hidden timer and store player times so time works a tie-breaker for the ranking, just showing this info to the player in case a tie happens (so to not put time pressure on players).
- No visible timers or score counter. The focus should be on geography, no pressure on the player. A move counter can be kept, as it's common in sokoban-like games, but it should be not intrusive.
- Similar to Stephen's Sausage Roll, let's use islands for the level design, with animated waves. Like Baba is You, the game should have animated decorative elements.
- Instead of a compass, the main player will be a humanized globe (a globe with a face) which will rotate when the player moves and have a idle animation. This globe should be south facing up (as per GeoJogos convention).
- Levels should load with a nice tile by tile transition.

Level generation ideas:

- Like many of the previous cited games, let's deviate from a rectangular level design, instead, levels should be generated using shapes of continents and subcontinents.
- The game will load a compressed GeoJSON of the entire world and select a group of countries (example: all countries in South America, or Africa, or North America and Caribbean, or West Europe, and so on) then render the shape of those countries as a puzzle-sized 2D grid (because we are reducing resolution, it will result on some areas having 100% land, some areas with 100% sea, and some between those values, we will use this info later).
- Then it will select some countries of the map and, at a random place next to where those countries are in the 2D grid, it will select places for the targets (e.g. a target for Brazil somewhere in Brazil, a target for Argentina somewhere next to Argentina and so on). It does not need to place those next to the capital city (or one of the capital cities) of the countries.
- Then it should select a sokoban level designing strategy (from those I mentioned in the links prior) and design obstacles (styled as mountains, trees and other geography elements) and place the boxes with flags (styled as just the country flags).
- It should check if the game can be solved using a sokoban level solver.
- There should be no hidden targets (i.e. the player and boxes can't be placed over the targets).
- On continents with few landmass (like Australia/Oceania/Australasia) the generator should switch from making sea an obstacle and make the level less like "Stephen's Sausage Roll" (where water can't be reached by the player) and more like "Baba is You" (where the player can move over the water). In this case, islands can be obstacles and the player can, instead, be on a boat.
- Sometimes just thresholding on 50% landmass over the downsized map would cause weird level shapes and impossible levels, so the generator can adjust this threshold dynamically to improve game design and solve solveability issues.

## Story mode

Story mode is a handcrafted geography-and-puzzle journey with the player and the Little Globe. Someone has misplaced flags around the world. Together they restore the flags, while Little Globe shares curiosities about the countries they meet.

The story follows three world tours. The first uses Easy presentation, with country flags visible at destinations. When the player and Little Globe return to the starting point, they find more mixed-up flags and glimpse a round silhouette running in the distance, too far away to identify. Destinations now show `?`.

The second tour uses Medium presentation. They restore the flags, return to the start, and discover another mix-up and another glimpse of the silhouette. The third tour also uses Medium presentation, with `?` destinations; the story has no difficulty selector or hard variants.

At the end of the third trip, they meet Compass. Compass explains that something strange happened while they were walking: they became disoriented and kept bumping into the flags. Little Globe notices a magnet stuck to Compass. The player and Little Globe remove it, the needle settles, and Compass returns to normal. All three become friends. Compass is not a villain.

The approved compass character has a round brass case, cream dial, face on the glass and a needle pivot at the center of the dial. Its magnet-attached pose has an independently moving, erratic needle. Earlier silhouettes conceal the face, dial and magnet. This is expressive cartoon motion, not a simulation of magnetism.

The route visits South America, North America/Caribbean, Eastern Europe, Western Europe, Africa, Asia and Oceania in that order. The current itinerary has 21 chapters: seven stops per tour, with the Caribbean map used on the third tour’s second stop. Existing boards are starting points for the human level-design pass, not finished curriculum. Story boards are edited in Tiled and stored directly; gameplay never replaces an authored board with a generated one. Transitions use the existing tile sweep, not a plane animation.

Start with easy, spacious boards, then gradually introduce Sokoban planning while keeping help and undo available. Include countries children may know less about, including those in Africa and Oceania. Dialogue, country curiosities and level layouts are separately editable. See `docs/STORY_AUTHORING.md` and `docs/STORY_FACTS.md`.

Design questions:

- Destination visibility is settled for Story: visible flags on tour 1, question marks on tours 2 and 3. Daily/Archive difficulty remains independent.
- Should the random seed be visible in random mode, so players can challenge others in the same level they played on? In this case, how should this seed look like? A random number (like Minecraft) or something else?
